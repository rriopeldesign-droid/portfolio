The Idea

Real plans instead of swiping

DateNight starts with the date, not the profile. People post real plans with a place and a time: a coffee, a concert, a hike. Everyone else browses those plans, RSVPs to the ones they’d actually enjoy, and the host approves who comes.

I co-founded it in 2026 and designed and built it end to end, from its own design system to the lifecycle emails. The tagline says it in four words: Browse. RSVP. Date. No Swiping.

Design Decision

Browse and RSVP, instead of swipe

Swiping asks you to judge a face in a second. DateNight asks a different question: would I enjoy this evening?

So the core unit is a plan, not a person. A date card leads with what, when and where, and the host is a small avatar in the corner. You don’t match with someone and hope a plan follows. You RSVP to the plan, the host approves who joins, and the date already has a time and a place.

The three-message limit finishes the job. Chat opens 24 hours before the date, and three messages each is enough to say hi and sort out the details. The rest happens in person.

How I Ship

Staging first, then production, every day

I ship to staging and production daily. Every change takes the same path, and the database follows the same order as the code: staging first, then production.

  1. 01 · Branch

    Build it

    Each change starts on its own branch, built with Claude Code and type-checked before it goes anywhere.

  2. 02 · Staging

    Try it

    It merges into the staging branch, and Vercel deploys it to a staging site with its own Supabase database and test accounts.

  3. 03 · Test

    Break it

    I use it the way members would: signed in as two test people at once, in Chrome and Safari, with database rules checked for each.

  4. 04 · Production

    Ship it

    A pull request into main. If it touches the database, a schema check compares it with production. Merge, and Vercel deploys it live.
